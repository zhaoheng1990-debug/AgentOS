# Endogenous Group Problem Runtime

AgentOS CoreSlim 0.4.0-alpha.4 adds a group problem-definition runtime above the
existing P4 problem-space store. It starts from admitted evidence, anomalies,
and unresolved conflicts. It does not require a candidate research question to
be supplied in advance.

This is an implemented problem-emergence protocol, not proof that the generated
problems are better than human questions or the best question from one model.

## Cognitive Roles

| Role | Provider operation | Formal output | Visible prior messages |
| --- | --- | --- | --- |
| Problem Framer | `endogenous_problem_framing` | `PROBLEM_CANDIDATE_SET` | none |
| Problem Critic | `problem_candidate_adversarial_review` | `PROBLEM_CRITIQUE` | candidate set |
| Researchability Assessor | `problem_researchability_assessment` | `RESEARCHABILITY_REPORT` | candidate set |
| Agenda Synthesizer | `group_agenda_synthesis_and_selection` | `AGENDA_SELECTION_PROPOSAL` | candidate set, critique, assessment |

The Critic and Researchability Assessor are context, memory, Provider/model,
Runner/Harness, and credit identities of their own. Neither receives the
other's message. This prevents feasibility estimates from simply echoing the
critique and prevents criticism from being softened by implementation plans.

## Problem Candidate Object

Each internally generated candidate contains:

- a stable problem ID and a question;
- research object and exact project scope;
- the anomaly that triggered the question;
- rival explanations and a falsifier;
- admitted evidence references;
- expected Cbit gain, urgency, and novelty estimates.

At least two candidates are required. IDs and questions must be unique. Scope
is an exact Runtime namespace, while the question, anomaly, and research object
carry the semantic boundary.

## Dynamic Provider Schema

Top-level array validation is not enough for problem objects. The Runtime builds
a stage-specific nested JSON schema for every Provider call:

- Framer scope is an exact enum and evidence refs are admitted enums;
- Critic and Assessor problem IDs are enums built from the actual Framer output;
- all risk, Cbit, falsifiability, tractability, novelty, urgency, and cost fields
  are finite numbers in `[0,1]`;
- Agenda selection IDs are constrained to the generated set plus `NONE`.

The Runtime repeats these checks locally. Provider-visible schemas support the
semantic work; local validation remains the enforcement boundary.

## State Machine

```text
PROBLEM_FRAMING
  -> PROBLEM_REVIEW
  -> RESEARCHABILITY
  -> AGENDA_SYNTHESIS
  -> CANDIDATE
```

Any stage can fail closed to `BLOCKED`. Retry preserves failed receipts and the
rejected Provider payload in the owning Agent's private quarantine log.
Invalidated evidence is removed from the admitted set before framing.

For `SELECT`, the selected ID must be:

1. generated by the Framer;
2. retained by the Critic;
3. independently marked researchable;
4. above the Runtime priority floor.

`STOP` is also valid and forms no seed.

## P4 And Seed Boundary

The existing `EndogenousAgendaLoop` remains the Runtime-owned problem store and
priority gate. `select_candidate()` applies the group Provider selection only
after deterministic eligibility checks. The resulting `AgendaSelection` never
authorizes execution.

A selected problem forms a hash-committed `DeliberationSeed` with:

- `PENDING_AGENDA_REVIEW` state;
- no execution authority;
- objective, research object, rivals, falsifier, operationalization, required
  Harnesses, unresolved conflicts, expected Cbit gain, and evidence refs;
- a reference to the group agenda-selection receipt.

`CognitiveDeliberationSession.from_deliberation_seed()` accepts this object only
with a separate Kernel authorization. It transfers the selected question and
seed provenance into coordination intake without silently promoting the seed.

CoreSlim 0.4.0-alpha.13 adds a second bounded consumer of the same seed.
`ProblemDefinitionStructureAdapter` verifies the seed, all four formal messages,
their execution receipts, and replay before constructing a problem-structure
candidate. Provider-supported dimensions still require a separate Kernel
admission before they can enter the organization-policy Selector. See
`PROBLEM_STRUCTURE_ADMISSION_RUNTIME.md`.

## Verified Live Behavior

The LIFE-COG3R live smoke supplied frozen evidence with
`seeded_problem_questions=[]`. The Framer generated three questions. The Critic
and Assessor independently processed the same candidate-set parent. The Agenda
Synthesizer selected the negative-control failure mechanism problem from their
surviving and researchable intersection.

The Kernel formed a pending seed, and a separate live Coordinator accepted it
as a `GENERATION` intake while candidate state remained `NOT_FORMED`. Both event
chains replayed successfully, and all 16 manifest files passed independent
SHA-256 and size verification.

This proves that the runtime path exists and is auditable. It does not yet prove
question quality superiority, long-horizon agenda learning, production
reliability, or autonomous authorization to execute research.
