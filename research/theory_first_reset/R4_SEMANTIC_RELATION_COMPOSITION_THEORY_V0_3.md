## Object Upgrading Audit

### Previous object

`ProviderSemanticRelationCoordinator`

Problem:

- it implies that Provider owns coordination;
- it conflates semantic relation judgment with deterministic arithmetic;
- it duplicates the existing `CognitiveCoordinationRuntime`;
- it creates another apparent state owner;
- it does not identify the minimal semantic quantity required for composition.

### Upgraded object

`SemanticPacketRelation`

The relation exists between two bounded cognitive packets. It describes whether
their information may be composed under the current scope and model.

The minimal relation states are:

1. `INDEPENDENT_DISTINCT`
2. `EXACT_DUPLICATE`
3. `DEPENDENT_DISTINCT`
4. `PARTIAL_OVERLAP`
5. `SCOPE_INCOMPATIBLE`
6. `UNRESOLVED`

The lift is accepted because it reduces rather than expands the engineering
surface:

- no new coordinator Runtime;
- no Provider arithmetic;
- one finite relation state;
- one deterministic plan compiler;
- one deterministic composer;
- explicit fail-closed states.

## Boundary And Excluded Claims

The theory claims:

```text
Semantic relation judgment can support Runtime composition
without granting the Provider composition or decision authority.
```

It does not claim:

- that six states cover all natural evidence relations;
- that Provider relation judgments are accurate;
- that dependence magnitude can be inferred without evidence;
- that blocked composition is positive cognition;
- that relation classification creates organizational surplus;
- that the objects are ready for CoreSlim integration.

## Causal Mechanism

For packet set `P` and pairwise semantic relation candidate `R`:

```text
Provider evidence support:
  packet descriptors -> candidate relation receipts R_candidate

Runtime canonicalization:
  R_candidate -> validated relation graph candidate R_graph

Runtime mechanical derivation:
  R_graph -> CompositionPlan

Runtime deterministic consequence:
  CompositionPlan + packet probabilities -> CompositionReceipt
```

The Provider cannot emit:

- final composition action;
- selected packet IDs;
- final composed probability;
- accepted, retained, or promoted state.

## Leading Model

The relation graph contains sufficient composition information when:

1. every packet pair has exactly one accepted relation;
2. all packet priors are compatible;
3. exact-duplicate components are internally probability-consistent;
4. all relations between distinct duplicate components are
   `INDEPENDENT_DISTINCT`;
5. no dependent, partially overlapping, scope-incompatible, or unresolved edge
   remains.

Then Runtime may:

- keep one canonical packet per duplicate component;
- combine canonical packet log odds;
- subtract duplicated prior log odds mechanically;
- produce a hash-bound composition receipt.

## Rival Models

### R0: relation state is insufficient

Additional numeric dependence or scope variables are required even for the
bounded synthetic system.

### R1: packet identity alone is sufficient

Provider semantic support adds no value because duplicate and independent
relations can be mechanically inferred from packet metadata.

### R2: fail-closed compilation is too conservative

Blocking dependence and overlap prevents harmful composition but destroys useful
coverage, producing safety by suppression.

### R3: relation graph is sufficient but Provider cannot instantiate it

The zero-Provider oracle graph passes; a later fresh Provider relation test
fails semantic accuracy or consistency.

## Discriminating Predictions

The zero-Provider construction predicts:

1. independent packets compose to the exact posterior;
2. exact duplicates are counted once;
3. duplicate-plus-independent graphs deduplicate then compose;
4. dependent, partial-overlap, scope-incompatible, unresolved, incomplete, or
   contradictory graphs block;
5. naive composition over exact duplicates produces measurable overconfidence;
6. removing any required edge can change an actionable graph to blocked;
7. no Provider is needed once relation premises are accepted.

## Falsification Conditions

The object model is rejected or revised if:

- a valid independent graph cannot reproduce the exact posterior;
- an exact duplicate is counted more than once;
- a blocked relation reaches composition;
- duplicate transitivity yields order-dependent plans;
- graph replay changes the result;
- composition requires a Provider call;
- the implementation needs a second coordination Runtime or state machine.

## Proxy Validity Limits

The first experiment uses oracle relation states and synthetic packet
probabilities. It validates contract and consequence construction only.

It cannot validate:

- natural-language semantic relation recognition;
- Provider calibration;
- source grounding;
- real evidence dependence;
- organizational Cbit;
- transfer beyond the finite construction.

## Anti-Additive Audit

Removed:

- `ProviderSemanticRelationCoordinator`;
- Provider-computed final probabilities;
- Provider-generated composition action;
- duplicate coordination state;
- deterministic direction and arithmetic duplication.

Retained:

- Provider-backed semantic relation support as a later candidate;
- Runtime-owned validation, graph compilation, gating, replay, and state;
- existing `CognitiveCoordinationRuntime` as the sole upper orchestration owner.

## Stop And Rollback

Stop the current version if:

- an object requires an unmapped theory variable;
- a second Runtime or durable repository appears;
- a blocked graph is composed;
- a test failure would require changing the frozen state taxonomy;
- Provider calls occur during v0.3A;
- CoreSlim, retention, or baseline state is written.

Any semantic taxonomy repair after reveal requires a new version.
